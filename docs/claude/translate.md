# Speech-to-speech translation (/translate)

_Split out of `CLAUDE.md`; see the task table there for which of these documents to read. Keep this file current in the same commit as the code it describes._

Provider measurements and `TranslationProviderSpec` details live in `TRANSLATION_BACKENDS.md`.

## Data flow

The `/translate` endpoint runs a parallel pipeline for speech-to-speech translation:

```
Bridge WebSocket (/translate)
    ↓
TranslatorProxy (translatorproxy.ts)
    ├─ One per WebSocket connection
    ├─ Reconciles `sources` control events into per-(source, language) connections
    └─ Routes media by tag to multiple TranslatorConnections
        ↓
TranslatorConnection (TranslatorConnection.ts) - One per (source, language)
    ├─ OpusDecoder - Decodes the speaker's Opus to PCM
    ├─ OpenAI Realtime translations session - PCM in, translated PCM + transcript out
    └─ OpusEncoder - Re-encodes the translated PCM to Opus for the return path
```

## Key components

**TranslatorProxy** (`src/translatorproxy.ts`)
- Manages a single `/translate` WebSocket connection (the bridge side)
- Reconciles `sources` control events (`exports` = sender source names, `requests` = synthetic `<source>.<language>` names) into one `TranslatorConnection` per (source, language)
- Routes incoming `media` events to the matching connection by tag; closes connections dropped from `requests`
- Also supports a dev `?lang=` path that seeds the initial target languages
- **The bridge socket's close is one info line, and its `error` is not an error of the session.** `onBridgeClosed` logs `TranslatorProxy bridge WebSocket closed: code=.. reason=".." wasClean=..` (the reason is the peer's string, quoted so it cannot split the line), appends the message of an `error` event that preceded it (`after error: ...`), tears every direction down without flushing the pacer (nobody can hear it) and emits `closed`, once. A close the proxy's own `close()` asked for (graceful shutdown) is reported as `TranslatorProxy closed the bridge WebSocket: ...` instead, so a rollout does not read as a run of bridge disconnects. The `error` listener records the message and logs workerd's "Network connection lost." at debug (`BENIGN_BRIDGE_ERROR_RE`); any other error (a reset connection, a bad frame in Node) stays at error. The JVB's `Exporter.stop` sends Close(1001, "closing") and then calls Jetty's `disconnect()` at once, cutting the TCP connection without waiting for the reply. In the Worker-hosted `/translate` that makes workerd fire the error "Network connection lost." on every normal bridge close (the invocation ends `responseStreamDisconnected`, as every WebSocket request does), which was logged at error before. The order varies: a client that mimics the JVB (Close(1001) then an immediate TCP cut) got the close event with 1001 first and the error in the same millisecond, while the real bridge sessions that prompted this logged the error with the teardown following from a close event whose code the old build did not log; workerd's close after an error carries 1006 and the reason "WebSocket disconnected without sending Close frame." Both orders are handled: that error goes to debug either way, and the close line carries its message when it came first. A client that sends Close(1001) and keeps the connection up gets the Worker's close reply within 30 ms and no error is logged, so the Worker does reply to a relayed Close (`server.close()` from `closed`, code 1005 as sent with no code). Node's `ws` delivers a Close frame as a clean close with its code, and also follows a real error with a close. `handleTranslate.ts` and `server.ts` act on `closed` (usage flush, `server.close()`), so the teardown is the same for both sequences
- Sends the server `info` message on connect (via `buildServerInfo(provider)`, where `provider` is the connection's speech-to-speech provider) and logs any inbound client `info` event, mirroring `TranscriberProxy`
- **Per-source voices.** With `runtime.config.xaiVoices` set and the provider xAI, the proxy passes each direction the voice its source id hashes to (`voiceForSource`, `src/translate/voices.ts`, via `TranslatorConnectionOptions.voice`), so a speaker sounds the same in every language, on every reopen and on every connection; the proxy logs a source's voice the first time it sees the source and again when a refused voice moves it, and at warn when every listed voice is refused and the configured or default voice applies; `loggedVoices` is pruned with the direction bookkeeping
- **Provider selection.** `TranslatorProxyOptions.provider` is the connection's speech-to-speech provider (`openai` or `xai`, `src/translate/provider.ts`), resolved by `server.ts` / `worker/handleTranslate.ts` with `resolveTranslationProvider` from the `provider` URL parameter or the deployment default (`TRANSLATION_PROVIDER`); an unknown provider (a client error) refuses the upgrade with 1008 / HTTP 400 and an unavailable one (no key, a deployment problem) with 1011 / HTTP 503 (`resolveTranslationProvider`'s `kind`), since every direction would fail at connect; in the Worker the `provider` parameter may have been written by the operator KV override (**Provider overrides** in `cloudflare.md`, the `translate` slot) before the handler sees it; the close reason is cut by UTF-8 bytes (`closeReason`) because it echoes the caller's value. Every `TranslatorConnection` of the proxy gets the same provider, and target languages are normalised per provider (`normalizeTargetLanguage(lang, provider)`: OpenAI's 13-language list, lowercased; for xAI any tag with the BCP-47 shape `isValidTargetLanguage` accepts, primary subtag lowercased and the rest as given, `zh-CN`); the deployment default comes from `resolveConfiguredTranslationProvider` (`TRANSLATION_PROVIDER`, unknown → openai with one warning), shared by both runtimes
- **A requested direction whose connection went away is reopened on the source's next media frame.** `desired` keeps the last `sources` state; `handleMediaEvent` reopens a missing (source, language) from it, so a direction closed by the provider (xAI drops a session after ~5 min without audio and caps one at ~2 h), by the idle close, or by a failure comes back without waiting for the next `sources` event. After an `error` close, or a `rejected` one (the provider closed the session within 30 s of creation: mid-handshake, right after it, or after a short run of audio; re-dialling that per frame or per round trip would be a paid session start each time), the reopen is paced per direction (`REOPEN_BACKOFF_BASE_MS` 1 s, doubling to `REOPEN_BACKOFF_MAX_MS` 15 s; media inside the window is dropped), cleared by a benign close and once a reopened session has carried 2 s of audio (`onSessionUsable`), so an isolated failure hours later starts from the base wait again; `idle`/`remote` closes reopen at once. The `onClosed` callback carries a `TranslatorCloseReason` for this. A `sources` event opens only the directions that are new: one in its reopen backoff, or one the idle close ended and no frame has reopened since (`idleClosed`), is left to the next media frame, because `sources` fires on every join and leave and re-dialling on each would start a paid wall-clock-billed session for every muted participant each time. A stale close from a connection a reconcile already replaced is ignored entirely (it must neither unregister the replacement nor touch its backoff), and the backoff of a direction dropped from `requests` is forgotten on the next `sources` event
- Owns the monotonic mediajson wire-envelope `sequenceNumber` for outbound `media` (per-proxy = per-WebSocket, which carries all synthetic sources); the per-source RTP sequence number is the separate `chunk` field from each connection's `RtpTimestamper`
- Re-emits each connection's talk boundaries as `talkStart` / `talkStop` events (payloads `TranslationTalkStartData` / `TranslationTalkStopData` in `src/translate/messages.ts`), drawing their `sequenceNumber` from the **same** wire-envelope counter as `audioFrame` / `media`, so a start/stop interleaves correctly with the media frames it brackets on the single outbound WebSocket. `server.ts` and `worker/handleTranslate.ts` serialize them to the `start` / `stop` mediajson messages
- `emitTranscripts` (`runtime.config.emitTranscripts`; Node resolves it from `config.translation.transcripts`, default true) controls whether target-language transcripts are emitted

**TranslatorConnection** (`src/TranslatorConnection.ts`)
- Manages one (source, language) translation stream
- **Two providers, one code path.** The provider-specific parts live in a `TranslationProviderSpec` (`src/translate/provider.ts`, `getTranslationProvider`): endpoint URL, key, requested subprotocols, the Node auth-subprotocol prefix (`openai-insecure-api-key.` / `xai-insecure-api-key.`; the Worker sends an `Authorization` header instead), the `session.update` payload, the handshake, whether the server sends transcript finals, the idle-close default, and language normalisation. OpenAI (`handshake: 'open'`): `session.update` on socket open, audio at once, `protocols: ['realtime']`. xAI (`handshake: 'session'`): the server speaks first with `session.created`, the connection answers `session.update`, and audio is held in the pending-PCM buffer until `session.updated` (`markConnected`); `HANDSHAKE_TIMEOUT_MS` (10 s) fails the direction if that never comes. xAI gets **no** subprotocol requested: with header auth it echoes none and a client that asked for one fails the handshake. Measured live (2026-10-27, `grok-realtime-translation-fast`): xAI's output audio is one burst per ~400 ms-endpointed source phrase at 7-900x real time, nothing during input silence; 100 ms appends behave like 20 ms ones; it never sent the documented `segment.usage`; and it does not answer the client's Close frame (the socket ends 1006 about a second later, logged at debug once `isClosed`)
- Decodes the speaker's Opus to PCM (`OpusDecoder`), forwards it to the provider's realtime translations session (OpenAI: model `config.translation.model` / `OPENAI_TRANSLATION_MODEL`, key `config.translation.apiKey` = `OPENAI_TRANSLATION_API_KEY` ?? `OPENAI_API_KEY`; xAI: key `XAI_TRANSLATION_API_KEY` ?? `XAI_API_KEY`, `XAI_TRANSLATION_URL`, optional `XAI_TRANSLATION_VOICE`, or the per-source voice `TranslatorProxy` assigns from `XAI_TRANSLATION_VOICES`, passed as `TranslatorConnectionOptions.voice` and by `buildSessionUpdate(language, voice)`), and re-encodes the returned translated PCM to Opus (`OpusEncoder`, with **DTX enabled** so libopus's VAD flags comfort-noise/silence frames — see talk boundaries below) for the return path
- Emits translated Opus frames (`onAudioFrame(tag, chunk, timestamp, payload, audioLevel, vad)`) and the translated (target-language) transcript (`onTranscription(transcript, targetLanguage, isInterim)`) — transcript **deltas** are `isInterim: true` and are incremental fragments (append-only, not a cumulative hypothesis) on both providers. OpenAI's endpoint sends no transcript-done event, so its **final** is the run's fragments concatenated and emitted at the talk-stop silence boundary (`finalizePendingTranscript`) and on close. xAI sends a per-segment `session.output_transcript.updated` whose `text` equals the concatenated deltas (measured), so with `provider.serverTranscriptFinals` that text is emitted as the final at once and the buffer reset, and `finalizePendingTranscript` publishes nothing on that provider (the silence timer landing between the deltas and the `updated` would otherwise print the segment twice; at close a segment whose final never came is dropped); it lands ~1.5 s after the source phrase ends and 0.3-6 s **before** the segment's audio (TTS queues behind a continuous speaker), so the subtitle leads the translated speech. Both suppressed when `emitTranscripts === false`
- Emits **talk boundaries** around each contiguous run of translated audio (a "talk"): `onTalkStart(tag, timestamp)` on the run's first frame (timestamp = that frame's RTP timestamp) and `onTalkStop(tag, timestamp, mediaInfo)` when the translated **voice** goes silent. The `/v1/realtime/translations` endpoint sends **no per-utterance boundary event** (only `session.output_audio.delta` + `session.closed`) and its output audio is *continuous* — a live mic's ambient noise keeps OpenAI emitting, so "audio present" is not a voice signal. Instead the encoder runs with **Opus DTX**: frames libopus flags as `inDtx` (comfort-noise/silence, including the periodic CNG updates) are **dropped — not forwarded to the bridge** — and do not count as voice; only non-DTX (voice) frames are sent and drive the talk. End-of-talk is inferred by a debounce timer (`armTalkSilenceTimer`) armed by voice frames (and, per above, transcript deltas), measured from the projected **media playout end** (`RtpTimestamper`'s `bufferAheadMs` — OpenAI streams faster than real time, so the consumer is still playing the burst after the last frame arrives) plus `TRANSLATION_TALK_SILENCE_TIMEOUT_MS`; sustained DTX/silence ends the talk and the next voice frame starts a fresh one. Because talks are bracketed by voice runs, a pause longer than the timeout splits a talk — tune granularity via `TRANSLATION_TALK_SILENCE_TIMEOUT_MS`. A talk also ends on close. (libopus emits a ~180 ms voice-flagged hangover before DTX engages, so a little trailing audio is forwarded past the end of speech; conversely, if the first frame of a run is classified DTX, no talk starts until the first voice frame — the intended behaviour.) Note: dropping DTX frames also drops libopus's periodic comfort-noise (CNG) refresh packets, so during silence the bridge's decoder gets no explicit comfort noise — it fills the gap via packet-loss concealment, and the `RtpTimestamper` inserts the real elapsed-silence jump on the next voice frame, so the client hears true silence rather than a splice. `endTalk()` is idempotent (a no-op when no talk is active), mirroring `doClose()`. The run spans the half-open `[start, stop)`: the stop timestamp is one frame past the last frame's (`lastFrameTimestamp + SAMPLES_PER_FRAME`), i.e. the timestamp the next contiguous packet would carry. `mediaInfo` = `{ bytesSent, duration }` — `bytesSent` is the run's total encoded Opus payload bytes; `duration` is the `[start, stop)` span in ms on the RTP clock (so it includes any inter-burst silence the `RtpTimestamper` inserted mid-run, and can exceed the wall-clock length of the bytes counted). The bridge turns start/stop into client-facing `SyntheticSourceSendingChangeEvent`s
- **Audio levels for the ssrc-audio-level header extension.** Every forwarded frame carries the encoder's `audioLevel` and `vad: true` (a forwarded frame is by definition non-DTX, i.e. libopus's VAD judged it voice). `TranslatorProxy` puts them on the `audioFrame` event and `buildTranslationMediaMessage` writes them as `media.audioLevel` / `media.vad` — the optional fields jicoco's mediajson `Media` already defines for the bridge→transcriber direction — so the bridge (`Conference.handleMediaEvent`) can write the RFC 6464 extension onto the injected RTP packet and clients can show a level for the synthetic source. The fields are **omitted, not nulled,** when absent, so a bridge that predates them sees the original message shape. The level never influences the bridge's loudest-speaker or default routing: injected packets bypass the endpoint receive pipeline, and `Conference.levelChanged` exempts synthetic sources
- RTP timing comes from `RtpTimestamper` (one continuous, monotonic timeline; see below) — there is no per-response timestamp reset
- **Translated audio is paced to real time before it leaves the proxy.** Both providers deliver output faster than real time, and xAI hands over each translated phrase, often several seconds of audio, in one burst of a few hundred milliseconds (measured 2026-11-04: 5.3 s of audio in 0.42 s). The bridge injects what it receives at once, and a WebRTC client's jitter buffer (NetEQ, 200 packets = 4 s by default) flushes when it overflows, so a listener heard only part of a long phrase while the transcript, carried over signalling, arrived complete — the "translations are missing things" report. So the encoded **voice** frames go through a `MediaPacer` (`src/MediaPacer.ts`, the pacer the `/agent` return path already used), which releases one frame per 20 ms at most `TRANSLATION_PACE_LEAD_MS` (`runtime.config.paceLeadMs`, default 200 ms = ten frames) ahead of the playout clock; `sendAudioFrame` runs on release. DTX frames are dropped before the queue (they take no release slot), the first frames of a burst go out at once (so the start of a phrase is not delayed), the `RtpTimestamper` and talk boundaries are unchanged (they already measured playout, and frames queued in the pacer keep re-arming the talk silence timer as they are released, so a talk cannot end while its audio is still waiting), and the idle close also waits for the queue to drain (the talk guard alone does not cover a disabled talk timer). Frames still queued when the direction closes are **released at once** (`MediaPacer.flush`, before `endTalk`, while `onAudioFrame` is attached): releasing them at real time would take time the connection no longer has, and dropping them would lose the end of the phrase the provider closed on or the tail of a direction the provider dropped mid-phrase; a burst at close is the pre-pacer behaviour for that tail, capped at 3 s (`FLUSH_AT_CLOSE_MAX_FRAMES`, the oldest frames; a longer burst would be partly discarded by the client's jitter buffer anyway, so the rest is dropped and the close is logged at warn instead of info). The owner skips the burst (`close(false)`) when nobody can hear it: the bridge socket closed, or the synthetic source was dropped from `requests`. The queue is capped at 15 s (`MAX_PACED_FRAMES`): translated speech can run longer than its source, so a continuous speaker builds up lag, and past the cap the **oldest** 3 s (`OVERFLOW_DROP_FRAMES`) are dropped as one block, so what is heard stays near the source at the cost of one clean skip (dropping one frame per push would punch a 20 ms hole per frame of the burst into the audio about to play, heard as a bad connection). The first drop warns once; the direction's total is logged at warn at close, and every drop counts in the OTel counter `otp_translation_paced_frames_dropped_total{reason}` on the container (`reason=overflow`, and `reason=close` for frames beyond the flush cap at a close with a listener; the translation metric batcher's own `translation_paced_frames_dropped` event is only the debug-log shim, and the Node runtime routes it to the counter); the Worker's metric sink is a no-op, so there the two warnings and the total at close are the record. Neither the cap nor the block size is an environment variable: both are policy for a case not yet seen in real use, and the lead is the one operator knob. The `RtpTimestamper` keeps its default 100 ms gap threshold: paced frames reach it a full lead ahead of their playout, so an event-loop stall registers only as idle time beyond the lead, and the threshold absorbs stalls up to about the lead plus itself. `TRANSLATION_PACE_LEAD_MS=0` disables pacing (the pre-pacer behaviour); the pacer raises a lead under one frame to one frame, since no frame could ever fit a smaller budget and nothing would be released (that livelock was reachable through `AGENT_PACE_LEAD_MS` before the pacer was shared). The value is parsed by `parsePaceLeadMs` (`src/translate/env.ts`) in both runtimes, which warns once about a non-integer (default applies), a negative (default applies), a sub-frame value (raised) or one over 2 s (accepted). Tests: `test/unit/TranslatorConnectionPacing.test.ts`; the talk-boundary and transcript tests run with pacing off so they drive the timer with raw bursts
- Latency instrumentation (the per-frame speech-RMS gate `pcmContainsSpeech` and the TTFA log) is debug-only (`measureLatency = config.debug`)
- **Idle close.** `idleCloseMs` (`TRANSLATION_IDLE_CLOSE_MS`, else the provider default: 0 for OpenAI, `XAI_DEFAULT_IDLE_CLOSE_MS` 120 s for xAI) closes a direction that has received no media for that long, counted from creation until the first frame, via a quarter-period `setInterval` check (`checkIdle`), with close reason `idle`; never while a talk is active, since translation lags the source and a speaker who finishes and mutes would otherwise lose the tail of the last utterance, nor while frames are still queued in the pacer (a deferral that lasts at most the 15 s queue cap once the provider stops producing, since the queue drains at real time). The Worker and the container both treat an unset or malformed value as unset (provider default), through the shared `parseIntOrUndefined` (`src/translate/env.ts`); the Worker warns once about a malformed one, the container's `config.ts` has no logger and stays silent. xAI bills the greater of audio and wall-clock time, idle included, and drops the session itself at ~5 min, so a muted participant would otherwise pay for silence and then lose the direction at xAI's timing; the proxy reopens it on the next frame
- `doClose(notify, reason)` is idempotent (guarded by `isClosed`) and detaches callbacks before teardown, mirroring `OutgoingConnection`; `onClosed(tag, reason)` reports a `TranslatorCloseReason` (`local`, `remote`, `rejected` = the provider closed a connection under `REJECTED_MAX_SESSION_AGE_MS`, 30 s, old, however much audio it carried; an older one is `remote`, so a muted participant's direction dropped by the provider's own idle timeout reopens at once, `idle`, `error`), and `error` always follows an `onError`. The provider WebSocket init is deferred to a microtask so the proxy's `onError`/`onClosed` are wired before a synchronous `new WebSocket` failure can fire; that path notifies `onError` and tears down
- Reports translated-audio usage **incrementally** via the optional `onUsageReport(durationSeconds, targetLanguage)` callback: a `setInterval` timer (period `runtime.config.usageReportIntervalMs`, `unref`'d so it never keeps the process/isolate alive) fires the audio duration translated **since the previous report** (`reportUsageDelta` = `(sentSamples − reportedSamples) / 24000`, where `sentSamples` is audio actually appended to OpenAI), and `doClose()` clears the timer and flushes the final remaining delta. The deltas sum to the direction's total. Incremental reporting (vs one cumulative report at close) means an abrupt kill — e.g. a Worker hitting its CPU limit — loses only the last partial interval, not the whole direction; it's billing-equivalent because billing is linear in duration and the usage endpoint sums each report's `duration_seconds`. The timer is started only when `onUsageReport` is set **and** the interval is `> 0`, so dev/replay sessions (no callback) start no timer

**RtpTimestamper** (`src/RtpTimestamper.ts`)
- Pure, clock-injectable generator of the RTP timestamp + uint16 sequence number for the 20ms translated-audio frames; used by `TranslatorConnection`
- Maps OpenAI's bursty, faster-than-real-time output onto one continuous, **monotonic** RTP timeline using a media-playout clock: advances by media duration per frame and inserts a proportional silence gap only when the source idled longer than the buffered media (`gapThresholdMs`, default 100). Guarantees the timestamp never decreases across response boundaries or bursts

## Translation runtime abstraction (container vs Worker)

The translation core (`TranslatorProxy`, `TranslatorConnection`, `RtpTimestamper`) is **runtime-agnostic**: it imports no `config`/`logger`/`metrics`/`ws`/codec modules directly. Everything host-specific is injected via a **`TranslationRuntime`** (`src/translate/runtime.ts`): `logger`, config values, metric sink + batcher, an outbound-WebSocket factory, Opus codec factories, and `buildServerInfo`. `IWebSocket` is the minimal socket surface common to Node `ws`, the Node global WebSocket, and the Worker WebSocket.

- **Node/container** — `createNodeTranslationRuntime` (`src/translate/nodeRuntime.ts`): existing `config`/Winston/OTLP, the Node global `WebSocket` (auth via the provider's `<prefix><key>` subprotocol, `OutboundWebSocketOptions.authSubprotocolPrefix`), and the codec facades (native/WASM per `OPUS_BACKEND`). Used by `server.ts` for `/transcribe` **and** `/translate`.
- **Cloudflare Worker** — `worker/translationRuntime.ts` + `worker/handleTranslate.ts`: the Worker handles `/translate` **directly** (a `WebSocketPair` `accept()`, no Durable Object — the accepted socket keeps the Worker alive for the session, and the bridge's pings keep it active). console logger, config from Worker env, no-op metrics, WASM codec (import-loaded, no fs — see below), and an **outbound provider socket via fetch-upgrade** (`ws(s)://`→`http(s)://` rewrite; auth via the `Authorization: Bearer` header — never both forms, which OpenAI rejects). The async fetch-upgrade is wrapped as a synchronous `IWebSocket` (queues sends/listeners until connected). `worker/index.ts` calls `handleTranslate` for `/translate`; `/transcribe` stays on the container (Worker outbound-connection limits — translate's fan-out is bounded by source×language). Requires `nodejs_compat`.
- **Worker-safe WASM codec**: `OpusDecoderWasm`/`OpusEncoderWasm` don't read `fs` at module scope — the Emscripten glue + compiled `WebAssembly.Module` are injected via `provideDecoderWasm`/`provideEncoderWasm`. Node registers them from disk (`src/OpusDecoder/wasmSourceNode.ts`, dynamic-imported by the facade only on the wasm path); the Worker imports them (`worker/opusWasmSource.ts`). Auth token is passed to the runtime as a neutral `bearerToken`; each runtime applies it its own way.
- **Guard**: `npm run check:worker-safe` (`scripts/check-worker-safe.mjs`, run in CI) fails if the core imports a Node-only module/API, so it stays bundlable for workerd. `npm run typecheck:worker` typechecks the Worker + imported core against `@cloudflare/workers-types`.

## Translation usage reporting (`src/usage-reporter.ts`)

Live-translation audio duration is metered so it can be billed downstream. It's **runtime-agnostic** (imports no `node:*`/config/logger — the url and a `Logger` are injected per report via `deps`), so it bundles into both the Node container and the Worker; it's on the worker-safe allowlist (`setInterval`/`clearInterval`/`clearTimeout` are globals, not Node imports).

- **Delta semantics**: each `TranslatorConnection.onUsageReport(durationSeconds, targetLanguage)` call carries the audio translated **since the previous report** (periodic while open + a final delta on close), not a cumulative total. `TranslatorProxy` wires that callback to `reportTranslationUsage(...)` — but **only when a `translationToken` is set** (the JVB-forwarded `X-Translation-Token`, threaded through `TranslatorProxyOptions.translationToken` in both runtimes). No token → no callback → no timer, so dev/replay `?lang=` sessions report nothing.
- **Batching**: `reportTranslationUsage` queues events and flushes at 50 events or 1000 ms (`flushTranslationUsage`), grouping by token (one POST per token, `Authorization: Bearer <token>`; body sends `duration_seconds` + `event_id` (a per-event idempotency key, a fresh UUID minted at the buffer push) per event — `targetLanguage` is local-logging only). Non-2xx → `logger.warn`; network error → `logger.error`; a 5 s `AbortController` bounds each POST. The module-level `buffer`/`flushTimer`/stashed `url`+`logger` and `warnedUnconfigured` are deliberately process/isolate-wide singletons (the usage URL is a deployment-wide constant and cross-connection batching is intended).
- **Close flush**: `flushTranslationUsage()` drains the final delta + any sub-threshold buffer. Node calls it on `SIGTERM`; the Worker calls it via `ctx.waitUntil(flushTranslationUsage())` in `handleTranslate`'s `proxy.on('closed', ...)` handler so the POST completes before the isolate is reclaimed. Without it the last interval's usage would be lost when the isolate is torn down.
- **Billing counter**: usage is billed from `sentSamples` (audio actually appended to OpenAI), not `totalSamplesSent` (all decoded audio) — so a session whose OpenAI socket never opens and drops its buffered audio isn't charged.
- Disabled (no-op, warns once) when `TRANSLATION_USAGE_URL` is unset. Interval configured via `TRANSLATION_USAGE_REPORT_INTERVAL_MS` (default 15000).

The CF Worker forwards `ENABLE_TRANSCRIBE`/`ENABLE_TRANSLATE`/`ENABLE_TEXT_TRANSLATION`/every other `TEXT_TRANSLATION_*` var/`TRANSLATE_TRANSCRIPTS`/`OPENAI_TRANSLATION_MODEL`/`OPENAI_TRANSLATION_API_KEY`/`TRANSLATION_PROVIDER`/`TRANSLATION_IDLE_CLOSE_MS`/`XAI_TRANSLATION_API_KEY`/`XAI_TRANSLATION_URL`/`XAI_TRANSLATION_VOICE`/`XAI_TRANSLATION_VOICES`/`TRANSLATION_TALK_SILENCE_TIMEOUT_MS`/`TRANSLATION_PACE_LEAD_MS` to the container (only when set, so container defaults apply otherwise) via `buildContainerEnvVars`. (In the CF deployment `/translate` is served by the Worker, not the container; the translation vars matter for a standalone container that serves `/translate` itself.)

## Transcript messages

`/translate` transcript messages use inner `type: "realtime-translation-result"` (so jitsi-meet recognizes them as a translation stream and does not render them in the CC panel like normal transcriptions) but keep outer `event: "transcription-result"` — JVB dispatches on `event` (via jicoco-mediajson) and forwards the payload, including the inner `type`, verbatim, so no JVB change is needed and old clients ignore the unrecognized `type`. Deltas are `is_interim: true`; the transcript-done event is final. Interims are sent to the client only when `sendBackInterim` is set. Note `sendBack` gates **transcripts only** on `/translate` — the translated **audio** (`media` events) is always returned to the bridge regardless of `sendBack`, since returning translated audio is the entire purpose of the endpoint (both `src/server.ts` and `worker/handleTranslate.ts`). The CF Worker dispatcher path forwards `realtime-translation-result` finals (in addition to `transcription-result`) to the dispatcher under `useDispatcher`; the Worker-hosted `/translate` forwards its finals to the per-session Dispatcher DO the same way (`worker/handleTranslate.ts`).

Both the Node server and the Worker handler build these messages via the shared builders in `src/translate/messages.ts` (`message_id` uses a per-connection sequence counter — never `Date.now()`, which collides for same-tag events within one millisecond), so the two serializers cannot drift.

## Environment variables

- `TRANSLATE_TRANSCRIPTS` - Emit target-language transcripts from `/translate` (default: true; false → translated audio only)
- `OPENAI_TRANSLATION_MODEL` - Speech-to-speech translation model (default: `gpt-realtime-translate`)
- `OPENAI_TRANSLATION_API_KEY` - Separate key for translation (default: falls back to `OPENAI_API_KEY`)
- `TRANSLATION_PROVIDER` - Speech-to-speech provider for `/translate` connections that pass no `provider` URL parameter: `openai` (default) or `xai`. A connection naming a provider whose key is unset is refused
- `XAI_TRANSLATION_API_KEY` / `XAI_TRANSLATION_URL` / `XAI_TRANSLATION_VOICE` - xAI realtime translation: the key (falls back to `XAI_API_KEY`; the team needs the realtime-translation entitlement or every upgrade is a 403), the endpoint (default `wss://api.x.ai/v1/realtime/translations`) and the TTS voice (unset → xAI's default)
- `XAI_TRANSLATION_VOICES` - Comma-separated xAI voice ids to spread speakers over (`src/translate/voices.ts`): each source speaks in the entry its id hashes to (FNV-1a), the same on every direction, connection (the bridge spreads a conference's directions over connections as jicofo's `translation.mode` says, one per exported source by default), isolate and reconnect, with no state (a rejoining participant has a new source id); collisions are the price, and a longer list lowers them. Set, `XAI_TRANSLATION_VOICE` applies only once every listed voice has been refused. A voice xAI does not know fails, once per process, the directions already opened with it: the proxy learns it from xAI's error (`markVoiceRefused`) and the sources that hash to it take the next entry from their reopen on; with the whole list refused the single `XAI_TRANSLATION_VOICE` applies, and with that refused too no voice is sent. The refused set is per process or isolate and lasts until restart, so isolates learn a bad id independently (a source may briefly differ across connections) and a corrected variable does not un-refuse the old id until restart; a source's voice change is logged
- `TRANSLATION_IDLE_CLOSE_MS` - Close a translation direction with no media for this long and reopen it on the next frame (default: unset → never for OpenAI, 120 s for xAI; `0` disables)
- `TRANSLATION_USAGE_URL` - Endpoint that receives live-translation audio-duration usage reports (see "Translation usage reporting"). Unset → usage reporting is a no-op (dev/replay runs and deployments without the endpoint cost nothing)
- `TRANSLATION_USAGE_REPORT_INTERVAL_MS` - Interval between periodic incremental usage reports for an open translation direction (default: 15000; `<= 0` disables the timer so only the final delta at close is reported). Resolved by both the Node and Worker translation runtimes
- `TRANSLATION_TALK_SILENCE_TIMEOUT_MS` - Silence timeout (ms) for detecting the end of a translated-audio "talk". The `/v1/realtime/translations` endpoint streams output-audio deltas with no per-utterance boundary event, so a talk ends when the output goes silent and the next delta starts a new one (drives the `SyntheticSourceSendingChangeEvent` sent to clients). Measured from the projected media playout end (OpenAI streams faster than real time, so the consumer keeps playing a burst after the last frame arrives), not from frame arrival. Default 350; must exceed the RtpTimestamper 100ms gap threshold. `<= 0` disables silence-based inference — unsafe for `/v1/realtime/translations` (which sends no boundary event), where it would mean a talk never ends until the connection closes; only disable against an endpoint that emits explicit done events. Resolved by both the Node and Worker translation runtimes
- `TRANSLATION_PACE_LEAD_MS` - How far ahead of real time (ms) translated audio may be released to the bridge (default: 200). The providers deliver a phrase's audio in a burst far faster than real time, and a burst longer than a client's jitter buffer (about 4 s) makes the client flush and lose part of it; the pacer releases one 20 ms frame per 20 ms instead. `0` disables pacing. Resolved by both the Node and Worker translation runtimes
