# Transcription backends (provider-specific behaviour)

_Split out of `CLAUDE.md`; see the task table there for which of these documents to read. Keep this file current in the same commit as the code it describes._

Measured provider behaviour and the `TranscriptionBackend` contract itself live in `BACKENDS.md`; this file holds the proxy-side handling of each provider.

**OpenAI**
- Uses Server VAD (Voice Activity Detection)
- Sends PCM audio
- Supports confidence scores
- Real-time streaming transcription

**Deepgram**
- Passes raw Opus/Ogg through by default (`DEEPGRAM_ENCODING=opus`); set `DEEPGRAM_ENCODING=linear16` to decode to PCM first
- Supports punctuation, diarization, language detection
- Streaming results with interim and final transcripts
- When `DEEPGRAM_DIARIZE=true` and word-level `speaker` indices are present, results are split per speaker segment; each message carries a `speaker: number` field
- `DEEPGRAM_MIP_OPT_OUT=true` adds `mip_opt_out=true` to the WS URL (opts out of Deepgram's Model Improvement Program; default false). Overridable per-connection via the `deepgram_mip_opt_out` URL query param, which flows `ISessionParameters` → `TranscriberProxyOptions` → `BackendConfig.deepgramMipOptOut`; `DeepgramBackend` resolves `backendConfig.deepgramMipOptOut ?? config.deepgram.mipOptOut`. The CF Worker forwards `DEEPGRAM_MIP_OPT_OUT` to the container via `buildContainerEnvVars`
- When Deepgram provides `alternative.languages`, the first entry is always set as the `language` property on the `TranscriptionMessage` (both standard and diarized paths), unconditionally. `DEEPGRAM_INCLUDE_LANGUAGE=true` additionally appends the language as a text suffix (e.g. `[en]`) — these are independent behaviours

**Gemini**
- Multimodal model (primarily used for audio here)
- Real-time API with WebSocket
- Sends PCM audio

**xAI**
- Uses xAI's WebSocket STT API (`wss://api.x.ai/v1/stt`); config entirely via URL query params (no session message)
- Auth via `Authorization: Bearer` header — passed using Node.js/CF Workers-specific third argument to `WebSocket` constructor (cast via `as any`)
- **Handshake failures: diagnostics + bounded retry.** xAI rejects the WS upgrade with an HTTP response when its STT backend is unavailable (observed at scale on 2026-09-10: fleet-wide `503`s). `XAIBackend` attaches a `ws` **`unexpected-response`** listener, so it owns the abort (that listener suppresses `ws`' generic `"Unexpected server response: <code>"` error) and logs everything xAI support asks for on a failed call: `status`, `requestId` (first of `x-request-id`/`x-requestid`/`request-id`/`x-amzn-requestid`/`cf-ray`), `retryAfter`, the full response `headers`, the response `body` (bounded by a 1s read timeout — the retry waits on it, and the body is diagnostics only, so the read never rejects), and the request `url` incl. query params. The **successful** handshake's request id is captured from the `upgrade` event into `this.requestId` and appended to every later failure log for that stream (`xAI WebSocket error …`, `xAI API error …`, close), so a mid-stream failure is traceable too. Retry: `connect()` makes up to `XAI_CONNECT_ATTEMPTS` (4) attempts for **every** upgrade rejection except an auth failure, and for pre-open transport errors; only `XAI_FATAL_UPGRADE_STATUSES` (**401/403**) and a malformed `XAI_STT_URL` (which `new WebSocket()` rejects synchronously) fail fast. This is a **denylist** because the allowlist that preceded it was wrong twice in the same direction: it began as 408/425/429/500/502/503/504 (per xAI a 503 on STT means "temporarily unavailable, retry with backoff", explicitly not a 429), grew the Cloudflare 52x origin-failure codes 521/522/523/524/525/526/530 after the edge answered 521+525 on 2026-09-04, 522 on 09-08 and 521 on 09-09, and then on **2026-09-22** xAI answered **404** to every `/v1/stt` upgrade for 7 minutes fleet-wide (34 rejections across 5 colos) while 404 was explicitly listed as fail-fast, on the reading that it meant a wrong URL, i.e. our own misconfiguration. It did not: `server-timing: cfOrigin;dur=217` showed Cloudflare had reached an origin that answered the 404 itself, the body was empty with no error detail at all, and the same URL from the same build connected again the moment the incident cleared. **Nothing in an xAI rejection distinguishes "your request is wrong" from "our backend is missing", so the status cannot carry that decision** — and failing fast on a genuinely malformed request bought little anyway, since a bad URL or query param breaks every connection forever and is equally loud whether or not we spend ~2s retrying first. The delay is exponential backoff (`XAI_CONNECT_BACKOFF_MS`, 250ms base, doubling, ±25% jitter, capped 4s — ~1.75s worst case), unless the rejection carried a `Retry-After` (delay-seconds **or** HTTP-date, per RFC 9110), which **wins over** the computed backoff but is **capped** at the same 4s — audio buffers behind `connect()`, so we never hold it longer than that however long xAI asks (refusing to retry instead would not honour the header either: the owner tears the connection down and the next media frame opens a fresh one immediately). For that same reason, when the attempts are exhausted on a transient failure the delay we would have waited is left behind as a **process-wide cooldown** (`connectCooldownUntil`, module-level, shared by every `XAIBackend` in the process since an outage is process-wide): the next `connect()` — the fresh backend the participant's next media frame creates, or a `recoverBackend` reconnect — first waits out the remainder (≤4s, `close()` cuts it short too). Without it an outage degrades into a per-participant hammer loop at one attempt-burst per RTT. `resetXAIConnectCooldown()` is a test hook. Each attempt is bounded by a `handshakeTimeout` (5s) — `ws` sets none by default, so an endpoint that accepts the TCP connection then goes silent would otherwise hang `connect()` for minutes, and the retry loop would stack that serially; `close()` also cuts the backoff wait short (`abortConnectWait`) instead of leaving `connect()` parked. A failed attempt's socket is **abandoned** (`abandoned` flag): its late `error`/`close` events log at debug and must never reach `onError`/`onClosed`, or the retried connection would be torn down under us; while an HTTP rejection's body is being read, `rejectionPending` keeps a dying socket from replacing that status as the failure reason. **Log levels / volume:** an attempt that will be retried logs at `warn`; only the final failure the caller sees is an `error`, and the full `headers` + `body` go on the first and final attempt only (intermediate retries log status/requestId/retryAfter and don't read the body) — in a fleet-wide outage every participant makes several attempts every few seconds, and ~3KB per attempt at error level to the log pipeline is its own incident. A `close()` mid-handshake or mid-wait (participant left) is not a provider failure: `connect()` logs it at `info` ("connect abandoned"), writes no metric and throws without `onError`. **Metrics:** every failed attempt (including ones a retry then recovers from) increments the OTel counter `otp_backend_handshake_failures_total{provider="xai", reason="http_<status>"|"transport"|"timeout"}` — the pre-existing `writeMetric(... errorType: 'upgrade_http_<status>' / 'handshake_error')` calls are only a debug-log shim, so this counter is what dashboards should use to see blips the retry absorbed. After the last attempt the historical behaviour is unchanged — `onError('websocket_error', …)` (errorType deliberately kept stable so `otp_backend_errors_total{type="websocket_error"}` and the alerts on it keep their meaning; the status + request id ride along in the *message*) then `close()`. That series now reports a lost connection only after the retries (2–22s) instead of immediately, so its rate during an outage is lower than before for the same provider health. **Its alerts need no threshold change:** `OTP_Backend_Errors` (`for: 2m`, warn) and `OTP_Backend_Errors_Sustained` (`for: 15m`, severe) in `infra-provisioning/nomad/prometheus.hcl` both fire on `sum by (env, job) (increase(otp_backend_errors_total[5m])) > 0`, and a `> 0` threshold cannot miss an outage because the rate dropped. What does change is that transient blips the retry absorbs no longer reach that series at all — the intended noise reduction (prod baseline over the 7 days to 2026-09-10 was sparse 2–10/hour scatter, against 421/hour at the peak of the fleet-wide 503 incident), but it also means those alerts no longer give early warning of xAI flakiness. `otp_backend_handshake_failures_total` is the series to watch (and to dashboard/alert on) for that. A connect failure stays **fatal** (not `recoverable`): reporting it as recoverable would race `initializeBackend`'s own catch, which tears the connection down. No model or region parameter is sent to xAI (xAI's STT default applies); `xai_stt_endpoint` only selects which configured URL the connection opens
- Sends xAI binary audio frames in one of two formats, chosen by `XAI_ENCODING` (`config.xai.encoding`): **`l16`** (default) decodes the client's Opus to signed 16-bit LE PCM at 16 kHz (`getDesiredAudioFormat()` returns `{ encoding: 'l16', sampleRate: 16000 }`, the `XAI_SAMPLE_RATE` constant; 16 kHz is xAI's native rate per their STT docs, and the Opus decoder outputs it directly); **`opus`** passes the client's **raw** Opus packets through unchanged, one per frame (`getDesiredAudioFormat()` returns the constant `{ encoding: 'opus', sampleRate: 48000 }`, so `AudioDecoderFactory` picks `PassThroughDecoder`; a constant rather than a copy of the input, so a `start` that only changes the client's sample rate or channel count does not reconnect the stream), and the stream URL declares `encoding=opus` with no `sample_rate` (xAI ignores it for Opus). Verified against xAI: same transcript, speaker labels and word timestamps as PCM, same `is_final` cadence; it saves a decode per participant and the PCM bandwidth to xAI. Only bare `opus` input is passed through: `ogg` input is still decoded, since xAI wants bare packets. `negotiatedFormat` records the choice for `buildStreamUrl` (same pattern as `DeepgramBackend`). Caveat: no packet-loss concealment on this path. Channel count is not one: a one-channel Opus decoder downmixes a stereo-encoded packet itself, so mono- and stereo-encoded WebRTC audio both pass; only multistream (surround) Opus would differ, and that needs framing we do not pass through
- `forceCommit()` finalizes the trailing utterance when the stream goes idle **without closing the WS**, by sending xAI's documented client message `{"type":"finalize"}` (`XAI_IDLE_FLUSH=finalize`, the default), which forces the current utterance out as a `speech_final` (measured ~0.15 s) and leaves the stream open. The older method, injecting `endpointing` + `XAI_IDLE_SILENCE_MARGIN_MS` (300) ms of 16 kHz PCM zeros so xAI's VAD crosses its threshold, is kept behind `XAI_IDLE_FLUSH=silence` as a rollback and applies only on the `l16` path (the raw-Opus path always uses `finalize`, there being no PCM silence to inject). `audio.done` is the other flush and closes the WS (code 1006), forcing a full teardown + cold start of the next utterance; #94 had made this a no-op for that reason, which left the trailing utterance before a pause/mute unfinalized. Either flush arms the idle turn end (`XAI_IDLE_TURN_END_GRACE_MS` after it, plus the silence length on the silence path). xAI's own `"ASR stream timed out"` on a long idle is still handled by the recoverable-reconnect path above
- xAI closes the ASR stream after a stretch of silence with `{type:error, message:"ASR stream timed out"}`. `handleMessage` detects this (message matches `/timed out/i`) and calls `onError('api_error', message, /* recoverable */ true)` (metric `errorType: 'stream_timeout'`); other `type:error` messages are non-recoverable (`errorType: 'api_error'`, `recoverable === false`), except the failed-utterance message below. Either way the dead WS is still `close()`d — the in-place reconnect happens on the `OutgoingConnection` side (JIT-15901)
- **Failed utterance: the stream stays open.** xAI also sends `{type:error, message:"Transcription failed on the current utterance; will retry if the session continues"}` on a stream it keeps open (a few a day normally; ~300 in 14 minutes from 48 participants fleet-wide on 2026-09-30). The proxy used to treat it as fatal, which on a pre-#131 build closed the whole session's socket with 1011 each time. `handleMessage` now matches it on `XAI_UTTERANCE_FAILED_RE` (`/will retry if the session continues/i`, the clause that makes the claim, so a rewording falls back to the fatal path) and only logs at `warn` with the requestId: no `onError`, no `close()`, held segments stay held (the next `speech_final` or the idle turn end reconciles them, as after any turn xAI drops). Debug-shim metric `errorType: 'utterance_failed'`; it does **not** reach `otp_backend_errors_total`. If xAI closes the socket after it anyway, the `'close'` listener reports a plain remote close (`onClosed`, no `onError`, no backoff) and the next media frame reopens the stream. Guard against an open-but-broken stream: `consecutiveUtteranceFailures` counts these since the last non-empty `transcript.partial`/`transcript.done` (empty silence partials do not reset it); the `XAI_MAX_CONSECUTIVE_UTTERANCE_FAILURES`th (3) in a row takes the error path as **recoverable** (`errorType: 'utterance_failed'`), so `OutgoingConnection` reopens the stream in place, bounded by `MAX_CONSECUTIVE_RECOVERIES`
- `transcript.partial` with `speech_final=false` → interim; `transcript.partial` with `speech_final=true` → final (true utterance end, carrying the whole turn). Within a turn xAI commits segments with `is_final=true` (each carries its own segment's text; the interim text resets after it); `speech_final=true` is the definitive end, and a committed segment normally becomes a final only through it — unless the turn outlives `XAI_MAX_TURN_MS` (see the long-turn cap below), in which case the held segments are emitted as a final early. `transcript.done` fires at stream end and ends a turn in progress like a `speech_final` (`endTurn`): an empty one flushes what the cap holds, a non-empty one emits the rest of the turn (see the long-turn cap below for when one is ignored as a repeat). During silence xAI also sends `is_final=true` with empty text and no `words` (about every 2s); these are ignored and do not start a turn
- Detected `language` is a BCP-47 code (e.g. `"en"`) and is present on `transcript.partial` events. It is passed through verbatim from xAI (no transformation)
- When `XAI_DIARIZE=true` and words carry `speaker` indices, results are split per speaker segment (same pattern as Deepgram)
- `XAI_INCLUDE_LANGUAGE=true` appends language suffix (e.g. `[en]`) to final transcript text; `language` field is always set on final messages when detected
- **Segmentation = `endpointing` (silence), not `smart_turn`.** `endpointing` (silence ms before a final) is **always sent**, default **850ms** (`XAI_ENDPOINTING`; xAI's own default of 10ms is far too choppy). `smart_turn` is end-of-turn detection for a *multi-speaker single stream*; we run one WS per participant (no turns), and enabling it holds finals across mid-sentence pauses → very long chunks. So `smart_turn`/`smart_turn_timeout` are **opt-in**: sent only when `XAI_SMART_TURN` is explicitly set (`config.xai.smartTurn` defaults to `undefined`). `smart_turn_timeout` (default 500) is only sent alongside `smart_turn`.
- All three segmentation knobs are **per-connection overridable** via URL query params — `endpointing`, `smart_turn`, `smart_turn_timeout` — flowing `ISessionParameters` (`xaiEndpointing`/`xaiSmartTurn`/`xaiSmartTurnTimeout`) → `TranscriberProxyOptions` → `BackendConfig`; `XAIBackend` resolves `backendConfig.xaiX ?? config.xai.X` (same pattern as `language`/`deepgram_mip_opt_out`)
- **Named STT endpoints (`XAI_STT_ENDPOINTS`, URL param `xai_stt_endpoint`):** `XAI_STT_ENDPOINTS` is a JSON object that maps names to `wss` URLs (`config.xai.sttEndpoints`, a `Map`; `parseEndpointMap` in `src/config.ts` drops a bad entry with a warning that never prints the URL, and counts it in `config.xai.sttEndpointsDropped`). A connection that carries `xai_stt_endpoint=<name>` opens that URL instead of `XAI_STT_URL`. The caller picks a name, never a URL, so the xAI key cannot go to a host the operator did not configure. The name has the shape `ENDPOINT_NAME_RE` (`src/utils.ts`; a copy in `worker/vars.ts`, and a test in `configOverride.test.ts` checks that the two agree on a sample of names): 1 to 32 characters of a-z, 0-9 and hyphen, **the first a letter or digit**. The URL parameter is lower-cased before the check, but the keys of the map are not, so an entry named `EU` is dropped. A malformed name, **an empty value included**, is a 400 at upgrade (`extractSessionParameters`). That function runs in the container for every path, so the container's `/translate` and `/agent` also reject a malformed value. The Worker-hosted `/translate`, which production uses, never calls it and ignores the parameter. Only `/transcribe` uses the parameter. For a new session, `server.ts` closes with 1002 when the name is not configured **or when the resolved provider is not xAI** (a `PROVIDERS_PRIORITY` change or a missing xAI key would otherwise move the audio to another vendor and drop the name). `XAIBackend.resolveSttUrl` throws as a backstop. The Worker does not let an operator provider override cause that: a request with `xai_stt_endpoint` pins the `transcribe` slot (see Provider overrides in `docs/claude/cloudflare.md`). There is deliberately **no fallback to `XAI_STT_URL` or to another provider**, because a caller that names an endpoint, for example to keep audio in a region, must not be moved silently. **A resume is checked too** (`refuseEndpointMismatch` in `server.ts`): a connection that names an endpoint that differs from the one the session was created with, the default included, is refused with 1002 before the session is touched, so the current connection and the grace timer are left alone and the bridge can start a new session with a new `sessionId`. A connection that names none still resumes, and the log says which endpoint the session keeps. Each map entry must be a `wss` URL with no credentials, query or fragment, and surrounding whitespace is removed. At listen time the server logs the loaded names, or an error when an entry was dropped. In wrangler `vars` the value can be a string or a JSON object: `buildContainerEnvVars` forwards an object as JSON. A KV override that fails validation is rejected as a whole and the wrangler value stays (the Worker logs an error, without the value). The mechanism is generic on purpose: the Worker does not pick a name. The caller does, for example jicofo through its `url-template`, set per site or per customer
- **Granular finalization (roll-own, `XAI_GRANULAR_FINALS`, default OFF):** xAI commits a final only on its end-of-turn `speech_final`, which re-emits the WHOLE turn at once — so a long speaker's turn lands in the stored transcript AFTER other participants' short acks (the GT-meeting ordering bug). When enabled, `XAIBackend` instead runs `XAIGranularSegmenter` (`src/backends/XAIGranularSegmenter.ts`): it reconstructs xAI's growing hypothesis from the interim stream (chunk_finals are segment-wise and interims reset after each — `mergeBase()` handles both that and a hypothetical cumulative provider), commits a **stable prefix** once it's been unchanged for `XAI_GRANULAR_STABILITY_MS` (default 1000) holding back `XAI_GRANULAR_GUARD_WORDS` (default 3) volatile words, and batches frozen words into `XAI_GRANULAR_MIN_WORDS` (default 5)-word segments emitted as finals (the in-progress remainder is emitted as an interim, Deepgram-style). The end-of-turn `speech_final` is **reconciled** — only the trailing words not already committed are flushed from its authoritative text, so the whole-turn re-emit is never reprinted; reconciliation only appends, so the sole correctness cost is a prefix word xAI revised after we froze it (measured **0 word-edits** across the whole tuned grid on 12 live captures — the "slower ⇒ fewer edits" framing is moot, the floor is already 0; slower only buys latency-margin). A non-empty `transcript.done` is routed through the segmenter only when a turn is still active (`hasActiveTurn()`) to avoid duplicating a turn already ended by `speech_final`. Granular finals are scoped to the **non-diarized** path (diarization needs per-speaker hypotheses → falls back to one-final-per-turn). The recoverable stream-timeout reconnect is unchanged. Two things the long-turn cap work changed apply here too: granular commits made before the end of a turn are reported as `midUtterance`, so the owner keeps its idle force-commit armed after them, and, with the long-turn cap on, the `forceCommit()` idle flush is skipped when the granular turn already ended after the last audio sent and no turn has opened since (the segmenter's `hasActiveTurn()`, since the granular path never starts the cap's turn clock). Flag + the stability/guard knobs are overridable **per-connection** via `xai_granular_finals`/`xai_granular_stability_ms`/`xai_granular_guard_words` URL params (resolved `backendConfig.xaiGranularX ?? config.xai.granularX`); `XAI_GRANULAR_MIN_WORDS` is **global-only** (a batching detail, not per-connection). Tuned live in `unreal-agents/experiments/xai-vs-deepgram-finalization` (see `TUNING.md`)
- **Long-turn cap (`XAI_MAX_TURN_MS`, default 4000; 0 disables):** in the default one-final-per-turn mode (granular off, and always when diarized), xAI commits each segment of a turn with `is_final=true` (the interim text resets after each) and ends the turn with a `speech_final=true` whose text is the whole turn — normally the only final. A `speech_final` needs `endpointing` ms of silence, so a continuous speaker (or two people handing over faster than that) may never get one, and since jicofo connects with `sendBack=true` but not `sendBackInterim` the bridge then receives nothing. So `XAIBackend` holds the turn's committed segments and, once the turn is older than the cap, emits them as a final (per-turn timer, or the commit that finds the turn past the cap) and each further segment as it commits; the later `speech_final` emits only the rest. The design narrative, xAI's observed event shapes and every edge case live in **BACKENDS.md ("Long-turn cap")**; the invariants to keep are: (1) **early finals are `midUtterance`** (second argument of `onCompleteTranscription`; granular commits before the end of a turn too), so `OutgoingConnection` keeps its idle force-commit armed after them; (2) **the rest of a turn is found by aligning words, never by a literal prefix or a raw count** (`alignTurnRest`: the last emitted words, located within `anchorSlack` of where the count puts them, in UAX #29 word units on both the text and the `words`-entry path; the text rest is cut from the original string right after the last emitted word, dropping what closes it and keeping what opens the rest); its fallbacks prefer a repeat to a loss (a `speech_final` is the whole turn only when it starts with **exactly** the turn's first words; anything else is emitted whole) and **warn with word counts only** — transcript text is never logged above debug; (3) **what was emitted is a fixed-size record** (`EmittedTurn`: count, first/last few normalized words, last speaker, and the boundaries (`carriedAt`) at which it was `carried` from a turn that already ended — on idle without a `speech_final`, or as `lastTurn` — so a late `speech_final`/`transcript.done` and a turn xAI folds into the next one are reconciled, while a fresh turn's early finals align against their own count); (4) **held segments are never silently dropped**: they are flushed before `onError`, on a remote close, on an empty `speech_final`/`transcript.done`, on the idle turn end (`forceCommit()` arms it: `XAI_IDLE_TURN_END_GRACE_MS`, default 3s, after the idle flush, plus the silence length on the `XAI_IDLE_FLUSH=silence` path, with no `speech_final`), and before a `speech_final` that does not carry them (xAI reset mid-turn) — except a held segment shorter than an anchor, which cannot be told from a re-rendering and is discarded with a debug line; an owner-driven teardown drops them like the uncommitted interim text it always dropped; (5) **`forceCommit()` skips its idle flush only when a turn ended after the last audio sent and no turn has opened since** (the segmenter's `hasActiveTurn()` on the granular path); (6) **`XAI_MAX_TURN_MS=0` restores the pre-cap behaviour**: no turn clock, nothing held, no idle turn end, no idle-flush skip (granular included), a non-empty `transcript.done` always emitted — only the `midUtterance` flag on granular commits remains, since that fixes a granular bug of its own and `XAI_GRANULAR_FINALS` is its rollback. `lastLanguage` is also taken from a `speech_final`/`transcript.done`, so an early final of the next turn carries the right language. Segments are joined with `joinText` (no space between two pieces of a language written without spaces; whole code points, so Han outside the BMP counts). (7) **The release is paced by a word budget as well as the clock, and no block is longer than the hard ceiling unless it cannot be cut** (`XAI_TURN_SOFT_MAX_WORDS` 20 / `XAI_TURN_HARD_MAX_WORDS` 35): the held segments go out once they hold the soft budget and the last ends a sentence (`endsSentence`, `src/backends/sentenceEnd.ts`, Unicode `Sentence_Terminal`), or the hard ceiling regardless; what is held goes out first when the next segment would pass the ceiling; one segment longer than the ceiling is cut (`splitLongSegment`) into pieces between the budgets (half the ceiling as the floor when the soft budget is 0); and the **turn end is shaped the same way** (`emitShaped`: the whole turn, or the rest after early finals, is cut when over the ceiling, all pieces but the last `midUtterance`). Cuts land at the longest ≥250 ms inter-word pause that ends a sentence, else the longest pause, else the last sentence end in range, else, **only when the words carry timestamps**, the ceiling; a transcript with no timestamps and no sentence end in range goes out whole, over the ceiling. Counts are UAX #29 words throughout (`wordCount`), cuts fall only between `words` entries, and a piece's text is cut from xAI's own `text` by `cutTextBeforeWord` (the same cut `emitTurnRest` makes, so openers like `¿` stay with the rest) when the entries render to the same words, else rebuilt from the entries. A cut segment's first piece inherits the segment's first speaker label for its leading unlabelled words only when nothing was emitted under a speaker yet (`emitDiarized` otherwise gives them the prior speaker, split or not). Because the budget lets held segments coexist with early-emitted words, `flushHeldSegmentsNotIn` aligns the held words **after** the emitted ones when checking whether a `speech_final` carries them. Every release is a normal `flushHeldSegments`, so reconciliation is unchanged. The budget rarely fires before a 4-5s cap at normal speech rates; it matters at a longer cap, for an oversized single segment, and for the turn end. Global-only (no URL param)
- The CF Worker forwards `XAI_API_KEY` (as `''` when unset → provider disabled) plus any set `XAI_STT_URL`/`XAI_STT_ENDPOINTS`/`XAI_LANGUAGE`/`XAI_DIARIZE`/`XAI_INCLUDE_LANGUAGE`/`XAI_ENDPOINTING`/`XAI_SMART_TURN`/`XAI_SMART_TURN_TIMEOUT`/`XAI_GRANULAR_FINALS`/`XAI_GRANULAR_STABILITY_MS`/`XAI_GRANULAR_GUARD_WORDS`/`XAI_GRANULAR_MIN_WORDS`/`XAI_CONNECT_ATTEMPTS`/`XAI_CONNECT_BACKOFF_MS`/`XAI_MAX_TURN_MS`/`XAI_TURN_SOFT_MAX_WORDS`/`XAI_TURN_HARD_MAX_WORDS`/`XAI_IDLE_TURN_END_GRACE_MS`/`XAI_ENCODING`/`XAI_IDLE_FLUSH` to the container via `buildContainerEnvVars`

**Mistral**
- Uses Mistral's Voxtral realtime WebSocket API (`wss://api.mistral.ai/v1/audio/transcriptions/realtime?model=<MISTRAL_MODEL>`), auth via `Authorization: Bearer` header on the `ws` package (as for xAI)
- Sends 16 kHz PCM as base64 `input_audio.append`; `session.update` on open carries the audio format and the connection's `language` if any. Mistral rejects session changes after audio has started, so `updatePrompt()` only warns
- No per-utterance final event: deltas are collected, sent as interims, and emitted as a `midUtterance` final at each sentence end (`endsSentence`). `forceCommit()` sends `input_audio.flush`; the answering `transcription.done` turns the rest into a final (not `midUtterance`) and the session stays open
- Error code `3804` (idle timeout, ~30 s after unflushed audio) is recoverable; other errors are fatal. See BACKENDS.md for measured behaviour
- The CF Worker forwards `MISTRAL_API_KEY` (as `''` when unset -> provider disabled) and, when set, `MISTRAL_MODEL` to the container via `buildContainerEnvVars`

## Adding a new backend

Caption-shaping helpers already exist and are provider-neutral: `endsSentence` lives in `src/backends/sentenceEnd.ts` (shared by the xAI cap and the granular segmenter), and `heldSegment`, `splitLongSegment` and `cutTextBeforeWord` in `src/backends/XAIBackend.ts` are pure functions over a transcript and its `{ text, start, end, speaker }` words (see the long-turn cap notes under xAI). Deepgram and OpenAI can both return word timestamps, so a long final from either could be shaped the same way. A second backend that needs them should lift them next to `sentenceEnd.ts`, not reimplement them.

1. Create `src/backends/YourBackend.ts` implementing `TranscriptionBackend`
2. Add configuration to `src/config.ts`
3. Update `src/backends/BackendFactory.ts` to register the backend
4. Add tests in `test/unit/backends/YourBackend.test.ts`

See `src/backends/DummyBackend.ts` for a minimal example.
